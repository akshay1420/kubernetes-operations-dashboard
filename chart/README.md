# Kubernetes Operations Dashboard Helm chart

Install this chart once in a dedicated namespace. It can observe the whole cluster, while workload access and restart actions remain restricted to the namespaces you explicitly configure.

## Quick start

Create a private values file outside source control:

```yaml
# dashboard-values.yaml
image:
  repository: ghcr.io/<your-org>/kubernetes-operations-dashboard
  tag: "0.1.29"

# For private registries only.
imagePullSecrets: []

rbac:
  clusterWideActions: false
  allowedNamespaces:
    - application-a
    - application-b

auth:
  enabled: true
  users:
    - username: operator
      password: replace-with-a-long-unique-password
      role: write
    - username: observer
      password: replace-with-a-different-long-password
      role: read

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: k8s-dashboard.internal.example.com
      paths:
        - path: /
          pathType: Prefix
```

Install it:

```bash
kubectl create namespace kubernetes-operations-dashboard
helm upgrade --install kubernetes-operations-dashboard . \
  --namespace kubernetes-operations-dashboard \
  --values dashboard-values.yaml
kubectl -n kubernetes-operations-dashboard rollout status deployment/kubernetes-operations-dashboard
```

Do not commit `dashboard-values.yaml`. Use a secret manager, encrypted values mechanism, or `auth.existingSecret` for production credentials.

## Access modes

`read` login users can view data and logs. `write` login users can also use the restart actions. The backend enforces this role check; hiding a button is not the authorization mechanism.

Kubernetes RBAC is a separate enforcement layer. With the default `clusterWideActions: false`, the ServiceAccount can take operational actions only in `rbac.allowedNamespaces`. Leave the list empty until you have chosen the namespaces deliberately.

To enable operations in every namespace:

```yaml
rbac:
  clusterWideActions: true
```

This grants the UI ServiceAccount its limited operator role across the entire cluster. It does not permit secrets, exec, workload creation, or arbitrary resource deletion. Treat it as privileged access and protect the ingress accordingly.

## Authentication secret options

The chart can create `users.json` and a persistent session secret from `auth.users`. For an externally managed Secret, create it with both required keys and point the chart at it:

```bash
kubectl -n kubernetes-operations-dashboard create secret generic dashboard-auth \
  --from-file=users.json \
  --from-literal=session-secret="$(openssl rand -hex 32)"
```

```yaml
auth:
  enabled: true
  existingSecret: dashboard-auth
```

`users.json` has this shape (password hashes generated by `generate_users.py` are preferred):

```json
{"users":[{"username":"operator","role":"write","passwordHash":"pbkdf2_sha256$..."}]}
```

For a broader enterprise deployment, use an internal Ingress with TLS and an OIDC/SSO authentication proxy. The built-in login and Kubernetes RBAC remain useful as a second layer, but all dashboard users share one Kubernetes ServiceAccount. Kubernetes audit events therefore identify that ServiceAccount rather than each human user.

## Platform notes

The chart is cloud-neutral. Configure your container registry, Ingress class and annotations, DNS/TLS, and selected namespaces for the target environment. Pod/node utilization appears when the Kubernetes Metrics API is installed and authorized.

For a private registry, create an image pull secret in the release namespace and configure it:

```yaml
imagePullSecrets:
  - name: registry-pull-secret
```
